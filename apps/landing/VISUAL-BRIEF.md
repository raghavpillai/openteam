# Homepage feature visuals

Design direction for the copy draft. These notes are not additional page copy.
Use the existing product components where they fit. Each visual should show one
simple example of its section's feature, using clearly identifiable sample data.
Keep supporting labels inside the relevant interface. Avoid detached subtitles
and repeated explanations around the components.

The sections should have different compositions, with their copy integrated into
the example: a rotating worker roster and profile deck, a dark computer workspace,
apps feeding a shared context, a memory notebook, and a scheduled brief moving
through its preparation steps. Avoid repeating heading, paragraph, then large
rectangle throughout the page. Preserve the hero copy and example bots.

Automatic transitions should advance the example, with readable completed states.
Start each scene as it approaches the viewport and continue through hover, focus,
and selector clicks. Hold only while editing memory or viewing an opened file.
Sleep offscreen and in hidden tabs; do not show playback controls.
No reduced-motion variant is needed.

## Build the team you need

Show Chief of staff, Travel planner, and Finance manager as configurable worker
profiles. One selected profile reveals its role and a short instruction. Keep
the other profiles compact so the visual explains specialization at a glance.

## A computer of their own

Use the existing computer preview to show a worker's browser and a file saved in
the shared workspace. Switching workers shows a different browser session with
access to the same shared file. Avoid a diagram implying isolated servers.

## Bring your apps and data

Use the plugin component to show recognizable connected apps, one saved skill,
and the option to add a custom MCP connection. Keep account configuration out
of the main view. App logos should support the explanation rather than become
a second exhaustive feature list.

## They remember how you work

Show two short saved preferences, such as "Prefer morning flights" and "Keep
briefs short," with a later response applying one of them. Make the saved memory
visible and editable; avoid a brain animation or claims about model training.

## Leave recurring work to your team

The example is a daily meeting brief owned by the Chief of staff worker.

- Show the routine name "Today's meetings" and a weekday morning schedule.
- Show the workflow: today's calendar, previous conversations, preparation brief.
- Show one compact result with who the user is meeting and what to review before
  the call. Two sample meetings are enough; each has a name and one preparation
  item with a source link.

Keep this a scheduled routine. Do not add provider event subscriptions or an
automation-builder interface that the product does not expose.

## Workers that help each other

Adapt the existing team workflow component to one handoff. A Finance manager
shares a travel budget; a Travel planner uses it to narrow the itinerary. Show
the shared context in the exchange. Avoid a large network diagram or a long
simulated conversation.

## You stay in control

Show one existing approval card with an understandable action and the supported
approve/deny controls. A private-input state can show masked fields when needed.
Never show actual secrets or invent an automatic payment workflow.

## Take your team with you

Retain the separate iPhone section. Show the same conversation and result in
desktop and phone views, with the complete phone visible.

## Use the model you prefer

Use a compact provider selector with ChatGPT, Claude, API key, and compatible
endpoint options. This section needs little visual space.

## One command to get started

Use the existing installation component with the command and a short guided
setup preview. Keep prerequisites readable and the command easy to copy.
