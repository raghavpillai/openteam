# Grok Bot memory compatibility

OpenTeam implements the verified file-based Grok Bot memory lifecycle from host `ecc8113`, inspected September 12, 2026. This is a behavior port into OpenTeam's worker, database, and filesystem architecture. It is not a copy of Grok's inaccessible Temporal backend, and it does not establish identical learning quality across models.

The latest local implementation adds **desktop memory management** in a bot's conversation details: list, search, individual deletion, clear, and live refresh. These controls use the same canonical files and migration path as `RecallMemory`, including cleanup of this bot's historical room copies. Deletion refreshes primary and forked memory prompt caches; clear preserves conversation state, pending learning, and shared user/project stores. The final regression passed **360 tests**, all four affected package type checks passed, and the renderer production build and isolated browser checks passed. This is a dedicated OpenTeam UI over verified management behavior, not a claim that GrokBot ships the same panel. Notifications use OpenTeam's durable invalidation stream rather than copying Grok's active-store snapshot protocol. These changes **have not been deployed**. See [the controls implementation report](../../output/research/grokbot-memory-2026-09-14-controls/report.md).

The latest September 14 source changes address the native scope and tool-result differences: new explicit saves, automatic extraction, episode buffers, and dreaming evidence are bot-wide across rooms; the public write tool accepts only `agent`, `user`, and `project`; memory mutations return the captured server-style text. Existing room records retain their audience restrictions. An exact bot-wide forget also removes matching historical room copies owned by that bot. Cached guidance from the previous room-write policy expires on the next turn. These changes are tested locally and **have not been deployed**. See [the native-default implementation report](../../output/research/grokbot-memory-2026-09-14-native-default/report.md). The deployment and investigation paragraphs below describe earlier snapshots.

The subsequent [deep native audit](../../output/research/grokbot-memory-2026-09-14-deep-audit/report.md) adds **15 native prompts, 10 management operations, seven notification phases, and 55 evidence assertions**, without product changes. On a fresh Temporal bot, the host's management list and clear API returned empty lists while `RecallMemory` still retrieved its saved fact; the bot's own exact-forget tool removed the match. These host APIs are therefore not established as universal controls for server-backed memory. On the box path, clear removed saved facts but preserved the pending episode buffer and working context; duplication started with empty own memory and conversation; a random `sessionId` did not create fresh context. Automatic learning appeared after the visible reply. Native memory SSE emitted current-list snapshots only for the active store in the tested phases, with a roughly 50 ms debounce. The box dreaming bootstrap remained false; the server-memory gate was absent, and a false client Temporal gate coexisted with an actual Temporal fixture, so these bootstrap values do not establish private server settings. ## Implemented behavior

| Mechanism | Behavior |
| --- | --- |
| Turn eligibility | Hidden/empty turns are excluded; the legacy learner uses the reference short-chatter vocabulary, punctuation normalization, 40-character threshold, and question-mark exception. |
| Extraction context | Up to 100 current profile facts and 30 recent log facts, plus up to ten relevant archived facts. The 500-record archive lists profiles first, then logs, each by recency. Recent log selection uses the existing 30-day importance rank. |
| Extraction protocol | The reference `profile:`, `log:`, `note:`, `remove:`, and `NONE` output protocol, case/whitespace deduplication, line markers, and 500-character normalization. Notes persist as `[note]` log entries. |
| Corrections | Remove only text included in the supplied existing-memory context, then add replacements. Apply under the bot-file mutation lock and reconcile the database index. Unrelated facts and Markdown survive. |
| Episodes | Every six eligible turns by default; configurable interval. Pass full pending exchanges with absolute dates to the reference journal-summary prompt. Persist a dated `[episode]` log entry and clear pending turns even when summary generation fails or returns `NONE`. |
| Dreaming | An optional replacement for legacy extraction and episodes, still default-off. Existing 15-second debounce, hourly sweep, 24-hour review interval, and bounded queues are retained. |
| Synthesis and verification | The reference prompts and request shapes; strict JSON, at most 64 changes, supplied evidence citations, protected explicit entries, and conservative clock-only updates. Empty proposals skip verification. |
| Retry lifecycle | Up to three attempts covering proposal and verification together, including verifier rejection. Each attempt gets a fresh 90-second deadline; backoff starts at two seconds. Shutdown cancels pending inference/retry work. |
| Evidence bounds | Preserve the first and last 4,000 characters, plus the 24-character omission marker, when a side exceeds 8,000 characters. |
| Explicit protection | Read current origin metadata at synthesis commit, even when an explicit re-save left the Markdown fingerprint unchanged. This closes the reproduced update/removal race. |
| Synthesis commit | Capture facts and fingerprint from the same file contents; use global ordering across files; select the reference occurrence of duplicate facts; preserve proposal order; stage edits and replace each touched file once. |
| Evidence spool | Parse before bounding Unicode/JSON-escaped text. Return all spooled evidence to the scheduler, which selects the newest 12 after merging RAM and disk and cleans every consumed ID. Older overflow files are not replayed later. |
| Cancellation | Propagate worker cancellation through the HTTP request to the computer's provider completion. Caller cancellation and inference deadlines abort the underlying completion. |
| Recall and prompts | The inspected `RecallMemory` tool, own/user/project renderers, provenance labels, and exact character-budget stopping rules. Frozen prompt sections, delivery acknowledgements, and compaction refresh remain in use. A correction is reflected in the next replacement note; a change of memory audience resets the memory prefix. |
| Native memory scope | Explicit writes default to agent memory in every room. Automatic learning, episodes, evidence queues, and temporal dreaming review use one store per bot. The public write scopes are agent, user, and project. |
| Historical room records | Existing conversation records retain audience filtering and source tags. They are not promoted into bot-wide memory. Historical room episode buffers and evidence spools remain on disk/in the database, but the native scheduler no longer processes them. Exact bot-wide forget also removes matching copies from this bot's historical room partitions. |
| Scope enforcement | Tool calls use the memory context persisted on the active run, never an audience supplied in tool arguments. Group calls cannot read or write global personal user memory. Native write/forget responses are plain text; internal events and idempotency records remain structured. |
| Management controls | Authenticated bot memory list/delete/clear APIs, shared client methods, and a desktop dialog with search and confirmations. The list shows up to 1,000 logical facts with the complete count; clear removes every parsed fact, including entries beyond that limit. Non-fact Markdown remains. |
| Live management updates | Reconciliation emits content-free `memory.changed` invalidations for changed bot/legacy-room facts. The open view coalesces refreshes and rereads on reconnect or focus; stale reads cannot restore a deleted row. First-use migration runs before management to prevent database-only facts from being restored after clear. |

`memory-prompts.ts` uses the four inspected inference prompts with only the assistant name changed from Grok Bot to OpenTeam. Tests compare their hashes against independently generated reference hashes.

For line-protocol compatibility, untagged extractor text is accepted as a log fact, as in the reference implementation. `NONE` is the no-op response; the old `{"facts": [...]}` extraction and `{"narrative": ...}` episode formats are no longer used. Custom inference adapters and test doubles must use the current protocols.

## Configuration

| Environment variable | Default | Meaning |
| --- | --- | --- |
| `OPENTEAM_MEMORY_DREAMING` | `false` | Select synthesis instead of per-turn extraction and episodes. |
| `OPENTEAM_MEMORY_EPISODE_INTERVAL` | `6` | Eligible turns per episode. `SAND_MEMORY_EPISODE_INTERVAL` is accepted when the OpenTeam variable is absent. |
| `OPENTEAM_MEMORY_MODEL` | Empty | Optional `provider/model` for memory inference. A bare model ID uses the configured provider. |
| `OPENTEAM_MEMORY_REASONING` | Main setting, or `off` with a memory-model override | Independent memory reasoning level. |

Development and release Compose pass these settings to the worker. The inspected Grok host's synthesis factory selected `gemini-2.5-flash`; `OPENTEAM_MEMORY_MODEL=google/gemini-2.5-flash` selects that model through a connected Google provider. The default continues using the user's configured inference provider/model so existing installations do not silently require a new provider connection. This is an explicit adaptation, not an assertion of identical model defaults.

Existing agent/user/project files are read in place. The earlier additive schema update introduced `MemoryConversation`, conversation-index provenance, the run's memory context, and a prompt audience key. The native-default correction requires no new schema and preserves historical room records within their audiences. No feature gate or inference-provider connection changed. The live deployment was backed up and updated on September 13; the native-default correction described above is still local.

## Boundaries of the port

- Grok's newer server-backed memory implementation was not available. Its complete storage transactions, model selection, extraction pipeline, and retention policies cannot be copied or certified from the inspected host.
- Conversation-local memory and sibling sharing came from an exposed adapter contract rather than the tested native default. They now serve historical records; new writes and learning follow the observed native bot-wide behavior. Audience equality for those older records uses the single account owner plus sorted bot participants and room kind. Deployments currently have one human user, so a separate sender-owned user-memory store and cross-account team-sharing implementation are outside scope, not blockers. Grok's private human/team authorization graph is not reproduced. The existing group refusal for personal user memory remains an OpenTeam boundary.
- OpenTeam retains one working model context per bot across rooms, and its filesystem is shared. Audience filtering controls durable-memory retrieval and the newly supplied memory section; it does not erase earlier model messages or establish a new security tenant. Native box testing confirms similar working-context reuse in GrokBot. The private Temporal session graph remains unverified; its existence must not be presented as proof of strict room isolation.
- OpenTeam retains its PostgreSQL index, advisory locks, file watcher, and stricter validation of invalid Markdown calendar dates. This is not byte-for-byte filesystem/parser equivalence; the ported memory renderers are checked against reference outputs. The internal `synthesized` origin is mapped to the reference `synthesis` label for inference.
- Synthesis evidence capture remains a bounded in-memory queue with support for reading existing spool files. A crash-durable capture writer was not established in the reference and was not added here.
- Recall is lexical. Exact-text tombstones and deduplication do not imply semantic conflict resolution or forgetting all paraphrases. LLM outputs remain probabilistic even with matching prompts.


## Memory tool and conversation routing

The tool is **`RecallMemory`**. No separate `RequestMemory` or `request_memory` tool appeared in the captured runtime. `RecallMemory` searches persisted facts; `update_state` is the write/forget API.

- `query` must be a nonempty string. Optional `scope` accepts `agent`, `user`, or `all`; malformed values, including arrays, fall back to `all`. Optional `limit` defaults to 20 and accepts integers from 1 through 50.
- Distinctive Unicode word overlap ranks first, followed by recency. Case-insensitive substring search is the fallback only when there are no word-overlap matches. Dates, tier, writer/source tags, no-match responses, and the 4,000-character result budget match the inspected tool.
- The scan includes the complete indexed file archive, not just the prompt slice. The old 20,000-row reconciliation cap and 2 MB per-file ceiling were removed. Shared writer duplicates use the reference normalized text key, recency, and ordering. Manual edits are reconciled before searching.
- Conversation facts remain within the `agent` search candidate set, tagged `[this conversation]` or `[via session <id>]`. Project search is still through its memory files; adding a new `project` or `conversation` search enum would differ from the inspected tool.
- `update_state` accepts `agent`, `user`, or `project`; an omitted scope is `agent` in every conversation. Explicit `conversation` is rejected. User scope is refused in groups. Successful writes and forgets, duplicates, and missing exact facts use the captured server-style text with `RecallMemory` hints; Grok's box backend uses read/grep hints instead.
- Exact bot-wide forget additionally cleans up matching records in the bot's historical conversation partitions under its file-mutation lock. It preserves other bots' records, user/project shards, and different text such as an episode containing the old value. This historical cleanup is an OpenTeam compatibility measure, not a claimed Grok feature.

Historical conversation files live at `agents/<bot-id>/conversations/<memory-conversation-id>/memory/`, using the same `profile.md`, `log/`, and `.dreaming/` layout. `MemoryConversation` records the address and capture-time audience. Membership changes create a different audience identity; outdated or inaccessible sibling partitions are excluded from recall. Agent-wide facts remain visible in every conversation with that agent. Internal file adapters can still read/write historical partitions, but the public tool and automatic learner do not create new conversation facts.
