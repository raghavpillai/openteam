# Android live-server parity harness

`scripts/android/live-parity.py` provides one deterministic validation surface for the Android data path. It covers authentication discovery, client bootstrap, history pagination, attachment upload/download, message send, long-poll synchronization, reconnect cursor behavior, delivery lookup, and OAuth callback rejection.

The default contract mode performs no network I/O and requires no credentials:

```sh
python3 scripts/android/live-parity.py --contract
```

The same check is available through the Android QA wrapper:

```sh
bash scripts/android/qa.sh live-parity
```

Live mode uses only process environment values. The harness never writes them, includes them in diagnostics, or stores them in a report:

```sh
export OPENTEAM_PARITY_MODE=live
export OPENTEAM_PARITY_SERVER=https://your-disposable-openteam-server.example
export OPENTEAM_PARITY_USERNAME=qa-user
export OPENTEAM_PARITY_CREDENTIAL='provided-outside-the-repository'
python3 scripts/android/live-parity.py
```

Optional values:

- `OPENTEAM_PARITY_CHANNEL_ID` selects a channel instead of the first stable channel in the bootstrap response.
- `OPENTEAM_PARITY_CLIENT_ID` supplies a stable idempotency key for repeated runs. If omitted, the harness derives one from the server and channel without using a secret.
- `OPENTEAM_PARITY_OAUTH_CALLBACK_URL` optionally supplies a callback URL from a disposable OAuth authorization. It must target the configured server's `/api/v0/plugin-oauth/callback` path; the value stays in the process environment.

The live run creates one small text attachment and one parity message. Use a disposable QA account and channel because the server does not expose a general-purpose asset deletion route. The message client id is idempotent, so rerunning with the same values should reconcile the existing delivery instead of creating an unbounded set of duplicate messages.

Without `OPENTEAM_PARITY_OAUTH_CALLBACK_URL`, the OAuth check sends a deliberately invalid synthetic callback and expects the server to reject it as stale or failed. A successful provider authorization still requires a disposable configured OAuth connection, a real provider, and a browser callback; that setup remains an external acceptance requirement.

The harness does not replace the Kotlin shared-core tests. `SyncTests` continue to verify durable cursor ordering, SSE parsing, reconnect backoff, history paging, delivery journaling, and unauthorized recovery without a server.
