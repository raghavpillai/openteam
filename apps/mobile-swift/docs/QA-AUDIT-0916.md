**The native app is not ready to replace the React Native iOS app.** This audit found **19 open findings: 10 reproduced behavior/contract failures, 8 code-confirmed implementation gaps, and 1 intermittent desktop-input failure**. None of these new findings is marked fixed.

The highest-priority problems are the blocked send queue, broken plugin access, and missing native push notifications. Six new simulator checks reproduce missing reply/thread/search behavior. Passing the earlier feature suite did not exercise these cases.

Evidence: [failure screenshots and receipts](../../../output/swift-full-qa-0916/review/index.html), [six-capture contact sheet](../../../output/swift-full-qa-0916/audit-attachments/contact.png), and [all ten dark-reference side-by-sides](../../../output/swift-dark-reference-0916/review/index.html). P1 means a migration blocker; P2 means a significant behavior or usability defect.

| QA-05 | P2 | **Search cannot open a matching thread reply.** | Search for a branched reply and tap the result. | QA-06 | P2 | **Search ignores result-specific destinations.** | Tap a routine search result: it opens chat rather than that routine. [All results use the same action](../Sources/App/HomeView.swift#L474). The RN client handles routines and links separately in `apps/mobile/app/search.tsx:406`. |
| QA-07 | P1 | **A queued message for a deleted bot blocks messages to other bots.** | Queue messages to bots A and B offline; delete A on another client; reconnect. With no global outbox screen, the user cannot discard A's entry through normal navigation. Compiling and exercising the actual `AppStore` reproduced this; programmatically discarding A immediately allowed B to send. Receipt: `audit-outbox.json`. [Queue guard](../Sources/App/AppStore.swift#L481). |
| QA-08 | P2 | **Reaction/activity unread badges do not clear.** | Receive a bot reaction and read the conversation. Swift sends only `throughSequence`, omitting `throughNotificationSequence`. Against the production API and PostgreSQL, the native payload left unread count **1**; the complete payload reduced it to **0**. Receipt: `audit-notification-read.json`. [Read payload](../Sources/App/AppStore.swift#L415). |
| QA-09 | P1 | **Plugin bot-access lists fail against the production API.** | Open an installed plugin. Swift requests `limit=100`; the server's maximum is **60**, returning HTTP **400**, “limit is outside the supported range.” The access controls cannot load. Production receipt: `audit-plugin-access.json`. [Hard-coded page size](../Sources/App/PluginsView.swift#L222); server validation: `apps/server/src/routes/plugin-query.ts:39`. |
| QA-10 | P1 | **The plugin “Bot access” switch does not grant account access and can show the wrong state.** | This remains after fixing/bypassing QA-09. Enabling the switch only updates plugin/skill enablement; no `/grant` request is made. Production state showed skills enabled with **zero connected accounts granted**. If an account grant already exists, disabling the plugin leaves the switch visually on because its getter ORs the grant list with skill enablement. There is no native per-account grant control. Receipt: `audit-plugin-access.json`. [Getter and mutation](../Sources/App/PluginsView.swift#L141); production access service: `apps/server/src/services/plugin/access.ts`. |
| QA-11 | P2 | **Attachment validation accepts files the server cannot accept.** | Stage a 26 MiB PDF: native staging accepts it, then the production upload rejects it with **413**. Native applies the 200 MiB video limit to every file; the server permits only **25 MiB** for regular files. ZIP package import also advertises 25 MiB while the server permits 20 MiB. A retry cannot resolve either size mismatch. Receipt: `audit-attachment-limit.json`. [Native staging](../Sources/Core/Persistence.swift#L76), [ZIP check](../Sources/App/PluginManagementViews.swift#L263). |

## Code-confirmed gaps

These follow directly from the implementation and the existing client/backend contracts. They have not all been exercised on a signed physical iPhone.

| ID | Priority | What is wrong | Reproduction / implementation evidence |
| --- | --- | --- | --- |
| QA-01 | P1 | **Native push notifications are unimplemented despite the visible notification switches.** | Enabling “Bot notifications” only saves the bot preference. There is no native notification permission request, APNs registration, token transport, badge lifecycle, or push-tap navigation. Background replies/routines therefore have no working native alert path. [Switches](../Sources/App/SettingsView.swift#L155), [app lifecycle](../Sources/App/OpenTeamApp.swift). |
| QA-12 | P2 | **Computer gestures lost functionality from RN.** | At normal zoom, two-finger dragging pans the local `UIScrollView`; no remote scroll action is emitted. Two-finger right-click is absent. In Trackpad mode, dragging updates only the local pointer and returns before emitting a remote drag. The help text still says to use two fingers to scroll. Menu Scroll Up/Down and touch-mode drag are separate working paths. [Gesture handlers](../Sources/App/ComputerSurface.swift#L58), [trackpad return](../Sources/App/ComputerSurface.swift#L149), [help](../Sources/App/ComputerView.swift#L125). RN's corresponding paths are in `apps/mobile/app/computer/[botId].tsx:560`. |
| QA-13 | P2 | **Saving a group profile silently reorders its members.** | Open a group whose existing member order differs from UUID sort order and save a name/description change. Swift converts members to a set, then always sends `members.sorted()`. The server rebuilds ordinals from that array. This can change the stacked avatar/member ordering without a membership edit. [Save](../Sources/App/SettingsView.swift#L458); server: `apps/server/src/services/channel/group-administration.ts:478`. |
| QA-14 | P2 | **Custom avatar handling is incomplete.** | A group custom photo is never fetched: `ChannelAvatar` requires a bot before downloading an avatar. A bot's profile preview always shows the robot, even when it has a custom photo. Replacing an existing bot photo elsewhere does not invalidate its cache because the task key excludes the avatar revision/`updatedAt`. “Reset to default” also cannot clear a custom photo if the stored icon/color already equal those defaults. [Avatar loading](../Sources/App/OpenTeamApp.swift#L116), [profile preview/reset](../Sources/App/SettingsView.swift#L243), [conditional avatar patch](../Sources/App/SettingsView.swift#L435). |
| QA-15 | P2 | **OAuth handoff recovery is incomplete.** | Start provider sign-in from the installed-plugin detail screen and return from the browser. That screen has no foreground/status refresh or waiting/expired state and no Cancel sign-in action. The deeper Connection screen refreshes once on return, but neither implements the existing authorization-session UI/cancellation endpoint. The RN client has explicit waiting, reopen, expiry, and cancel controls. [Top-level sign-in](../Sources/App/PluginsView.swift#L110), [connection return handling](../Sources/App/PluginConnectionView.swift#L151), RN: `apps/mobile/src/components/plugins/plugin-authorization.tsx`. This is a UI/lifecycle gap, not a claim that every provider login fails. |
| QA-16 | P2 | **Saved custom headers/environment variables cannot all be cleared.** | In Connection → Advanced, enter `{}` to remove existing headers/environment values and save. Swift omits empty maps, so the server preserves the existing credentials. There is no explicit clear-all control or display of saved key names. The server supports replacing the maps with `{}`. [Omitted empty maps](../Sources/App/PluginConnectionView.swift#L247); server: `apps/server/src/services/plugin/configuration.ts:175`. |
| QA-17 | P2 | **Queued attachment-only messages have no visible attachment identity.** | Send an image/file while offline. `PendingMessageView` renders text and delivery status only; it renders neither staged files nor uploaded attachments. For an attachment-only send the user sees a bare queued/sending label, and after rejection cannot identify the file from the pending bubble. [Pending renderer](../Sources/App/ChatView.swift#L567). |
| QA-19 | P2 | **Custom MCP rejects valid endpoint URLs containing query parameters.** | Add an HTTP MCP endpoint such as `https://example.invalid/mcp?tenant=qa`. The form reuses server-base-URL validation, which rejects everything after `?`, although connection endpoints may contain query parameters and the server accepts them. [Wrong validator](../Sources/App/PluginManagementViews.swift#L472), [server URL restriction](../Sources/Core/API.swift#L60). |

## Dummy screens and incomplete native presentation

- **Confirmed no-op:** “Start a thread” inside a thread (QA-04).
- **Misleading available feature:** Bot notification preferences exist, but native delivery is absent (QA-01). Plugin access is also presented as a working control despite QA-09/10.
- **Functional but unfinished editors:** Plugin package definitions, supporting file maps, tool arguments, and advanced connection settings are raw JSON text editors. They call real endpoints; they are not finished native authoring/setup flows. Invalid JSON has error handling. [Package editor](../Sources/App/PluginManagementViews.swift#L278).
- **Informational only:** Preferences → Auto-review rules sends the user to the desktop app; it provides no mobile rule management. Help Center is a repository link. Send Feedback opens a share sheet with version text and does not submit a feedback ticket. These labels/flows need product acceptance; they are not equivalent to the reference's complete support/settings experience.
- **No sign-up/password-reset screen:** Both are disabled by the existing production authentication contract (`apps/server/src/auth.ts:37`). This is an unmet earlier registration request, not evidence of a broken Swift login or a safe endpoint that simply needs connecting.
- “No routines,” “No memories,” and “Starting desktop…” are real empty/loading states. The computer frame is interactive, and an actual scheduled worker execution was observed. They are not dummy screens.

## What passed, and what those passes do not establish

- **26/26** default UI checks on iPhone 16e, iOS 26.5. Authentication errors/cancellation/expiry, normal chat and lost acknowledgment, basic profile/group/memory/plugin flows, routine failure recovery, rich rendering, private media and handoff are covered by fixtures.
- **7/7** dark-reference checks on iPhone 16 Pro Max, plus **4/4** focused profile/routine checks on the compact phone. All ten supplied dark references have side-by-side captures and glass detail crops in `output/swift-dark-reference-0916/review/`.
- **25** Swift core checks and **278** RN/shared-client checks passed. Desktop robot source alignment also passed; the app uses our robot artwork.
- **48** production integration checks passed. A real five-minute schedule fired while the native app was terminated, ran the production worker/parent delivery path, and appeared after relaunch. Inference responses were deterministic; the scheduler and database were real.
- Two real Linux desktop integration checks passed, covering concurrent input order and multilingual typing. The latest native desktop repeat passed; retain QA-18's preceding failure.
- Debug tests and a Release **simulator** build succeeded. This is not signed-device acceptance.

**Why previous green tests missed problems:** the basic fixture treats enablement as account grants and accepts `limit=100`; production does neither. Its read endpoint always clears unread count and does not model the independent activity cursor. Its search fixture returns only message results. Those are coverage defects in addition to the app bugs. Passing that fixture cannot establish plugin, notification, or all-category search parity.

Still unverified: required-auth production login with a real account, real provider OAuth/tool use, physical microphone/camera/interruptions, APNs, full VoiceOver/Dynamic Type/landscape/iPad coverage, iOS 18 fallback behavior, process termination during a real upload/send, multi-account races, and sustained very large-history performance. Only iOS 26.5 simulators are installed here. The recording reference uses a labeled simulator-only synthetic AAC source because this Mac has no microphone input; actual transcription recognition and recording-device quality are not accepted.

The visual work is also not whole-app pixel equality. Native menu contents, the profile layout, the robot identities, and the desktop test content differ from the reference. Glass comparisons are rendered-color observations, not inferred alpha values.
