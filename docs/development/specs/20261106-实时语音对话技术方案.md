# 实时语音对话技术方案

日期：2026 年 11 月 6 日。修订：2026 年 11 月 7 日。

本方案在分支 `spec/realtime-voice-conversation` 上启动正式规格文档流程。

当前代码库已经支持文本 Agent 执行、持久化 channel message、Worker NDJSON 流、供其他功能使用的认证 WebSocket、批量语音笔记转写、桌面端麦克风采集、iOS 语音笔记、Android 语音笔记以及 Kotlin Multiplatform 移动端边界。但当前还不支持持久的双向实时语音会话。

拟采用服务端终止的处理链路：

```text
macOS / iOS / Android 麦克风（系统回声消除）
  -> 客户端 Opus 音频帧
  -> 经过认证的语音 WebSocket
  -> 服务端解码、重采样、VAD、流式 STT
  -> 现有 channel message 和 Agent run
  -> Agent 通过 SendToUser 发送的可见回复
  -> 服务端流式 TTS 和 Opus 编码
  -> 客户端播放
```

服务端不会收到客户端 Provider 密钥，也不会持久化原始音频。最终转写会成为普通的持久化 channel message。部分转写只保留在会话范围内。TTS 只朗读 Agent 通过 `SendToUser` 发送的用户可见回复，不朗读不对用户展示的助手文本，因此朗读内容与聊天历史一致。发生抢话时，服务端先只停止音频输出；只有新发言的最终转写被接受后，才由现有用户消息替代路径取消旧 run，咳嗽或附和声不会取消回复。

正式文档包括：

- [需求文档](../../../specs/002-实时语音对话/requirements.md)
- [设计文档](../../../specs/002-实时语音对话/design.md)
- [任务清单](../../../specs/002-实时语音对话/tasks.md)

第一阶段同时接入火山引擎豆包语音和 Deepgram 的流式 STT/TTS WebSocket，并将 Provider 细节封装在服务端适配器中。两个 Provider 都在配置界面提供选择，并分别进行能力和连接检查。第一个检查点是 macOS 服务端 Provider 和编解码验证。验证必须在开始 iOS 和 Android 实现前，测量 Opus 解码/编码可行性、流式 STT/TTS 行为、`SendToUser` 驱动的首段音频延迟、中断延迟、各平台外放回声消除、资源使用和清理情况。

任务清单按阶段排列，先验证高风险的媒体和 Provider 链路，再让三个客户端固定传输协议。方案同时保持现有语音笔记流程独立，以保留当前用户行为和现有测试覆盖。
