# OpenTeam for iOS — Swift native migration

A SwiftUI iPhone/iPad client for the existing OpenTeam HTTP API. This is a **migration beta**; Release builds update the existing iOS TestFlight app. Android remains in `apps/mobile`.

[TestFlight 0.0.1 (27)](docs/TESTFLIGHT-27.md) fixes Connect after Re-auth and updates sign-in copy, with signing, upload, and live HTTP QA evidence.

[September 18 full iPhone QA and performance](docs/FULL-QA-0918.md) is the current status, including the deployed local server/APNs configuration and remaining performance, VNC, visual and device acceptance work.

[React Native sign-in restoration](docs/AUTH-RESTORATION-0917.md) restores the animated bot field and glass welcome/server/account flow.

[Live remote-desktop/VNC validation](docs/VNC-QA-0916.md) includes three reference comparisons and the remaining native gesture and refresh-rate limitations.

The [full-app QA audit](docs/QA-AUDIT-0916.md) and [settings/plugin follow-up](docs/SETTINGS-PLUGIN-AUDIT-0916.md) originally recorded 22 findings and their evidence. The [native push follow-up](docs/NATIVE-PUSH.md) implements QA-01 and fixes the QA-08 read payload. [Live-server gesture QA](docs/LIVE-SERVER-QA.md) fixes QA-02 and verifies real model replies, held/swiped inline replies, attachments and relaunch persistence. The [September 17 triage](docs/QA-STATUS-0917.md) identifies the remaining priorities and the main worker’s missing APNs configuration. Earlier audit counts reflect their capture dates. The optional `QAAudit` scheme retains the original audit cases on independent fixtures at ports 20010/20011; its two attachment gesture checks now pass. `SettingsPluginAudit` adds the ten-screen comparison and four failing checks, using independent fixtures at 20013/20014. Both are excluded from the default suite; default passes do not mean the open audit findings are resolved.

Debug builds install as **OpenTeam Swift** (`dev.openteam.mobile.swift`) with their own Keychain, sandbox, and `openteam-swift://` links. Release builds install as **OpenTeam** (`dev.openbot.mobile`), use the existing app’s notification and Keychain identity, and handle `openteam://` links. Release version/build/team settings come from `release.json`. The application UI, navigation, animations and state run in Swift. This target has no React Native, Expo or CocoaPods dependency. Complex message documents use a small, isolated offline WebKit renderer with bundled Markdown, KaTeX and Mermaid libraries; ordinary messages and code remain native views. Native push adds backward-compatible APNs registration/delivery alongside the existing Expo transport.

## Run

Open `OpenTeamNative.xcodeproj`, select the `OpenTeamNative` scheme and an iOS simulator, and Run. iOS 18 or later and a Swift 6/Xcode toolchain are required. For a physical iPhone, choose your Apple signing team in both the app and notification-extension targets first; see [native push setup](docs/NATIVE-PUSH.md). Enter the same server address and OpenTeam account used by the existing app.

From the repository root:

```sh
xcodebuild -project apps/mobile-swift/OpenTeamNative.xcodeproj \
  -scheme OpenTeamNative -sdk iphonesimulator \
  -destination 'generic/platform=iOS Simulator' \
  -derivedDataPath apps/mobile-swift/.build-ios build

swift test --package-path apps/mobile-swift
```

The checked-in project is generated by `scripts/generate-project.py`. Regenerate it after changing target configuration; source files are picked up automatically through Xcode synchronized groups.

## Compare with the existing app

Start the isolated in-memory server in one terminal:

```sh
bun apps/mobile-swift/scripts/parity-server.ts
```

For the React Native reference, start Metro in a second terminal and launch its existing development build on a test simulator:

```sh
EXPO_PUBLIC_OPENTEAM_API_URL=http://127.0.0.1:19997 \
  bun --cwd apps/mobile dev --port 8081 --localhost
```

If that simulator already has an RN server saved, use its private-connection screen to select `http://127.0.0.1:19997`. Do not point these tests at a personal or production server. The harness uses synthetic data, resets in memory, and never runs a model or contacts a connected service.

For the Swift app, enter that same address. Its UI tests use DEBUG-only launch arguments `--ui-testing --server http://127.0.0.1:19997`; these create a separate temporary cache and do not save a login in Keychain.

Run the repeatable native test pass against a booted simulator:

```sh
bash apps/mobile-swift/scripts/verify.sh <simulator-udid>
```

The verification script starts independent loopback fixtures on ports 19997 (chat/delivery) and 19992 (account/features), checks the shared robot source, then runs core, RN/client-contract and 26 native UI tests. Functional writes are decoded using the production request schemas. Optional `LiveBackend` and `LiveComputer` schemes exercise the production server/worker/database and an actual disposable desktop; see [system QA](docs/SYSTEM-QA.md).

The `OpenTeamReference` scheme additionally runs `ReferenceCaptureTests` against the separately installed `dev.openbot.mobile` app. Start Metro first. The default `OpenTeamNative` scheme excludes this optional reference test, so ordinary Swift tests don't require an RN installation.

```sh
xcodebuild -project apps/mobile-swift/OpenTeamNative.xcodeproj \
  -scheme OpenTeamReference \
  -destination 'platform=iOS Simulator,id=<simulator-udid>' \
  -derivedDataPath apps/mobile-swift/.build-ios \
  -resultBundlePath output/swift-native-comparison.xcresult \
  -parallel-testing-enabled NO CODE_SIGNING_ALLOWED=NO test

python3 apps/mobile-swift/scripts/export-comparison.py \
  output/swift-native-comparison.xcresult output/swift-native-comparison
```

Use a new result-bundle path for each run. Screenshots are XCTest attachments in the result bundle. The export creates named images, the actual test summary, and a local side-by-side `index.html` comparison. See [the parity checklist](docs/PARITY.md) for what must pass before cutover.

## Structure

- `Sources/Core`: Codable API models, URLSession transport, message merging, atomic cache/outbox storage, and protected local attachment staging. Compiles as a Swift package for fast macOS unit tests.
- `Sources/App`: SwiftUI screens, a main-actor observable store, Keychain session storage, AVFoundation recording, PhotosPicker/camera, and Quick Look previews.
- `Tests/CoreTests`: protocol, HTTP transport, persistence, attachment and reconciliation tests. The bootstrap fixture comes directly from the RN fixture.
- `Tests/UITests`: actual simulator interactions and screenshots. Mutations are asserted against the isolated fixture server.
- `scripts/parity-server.ts`: a bounded contract fixture, not a second implementation of the product server. Passing fixture tests does not establish live-backend or worker parity.

## Delivery and lifecycle

A send is written to disk before clearing its composer. Its client nonce is stable across retries. The client checks the delivery endpoint before sending, preserves ambiguous or pending deliveries, and merges server echoes by ID/nonce. Attachments are first copied into protected per-account storage, then uploaded and journaled before the message is submitted. Drafts, cache and pending messages are scoped to normalized server plus account ID; secrets remain in Keychain or transient secure input fields.

The foreground client uses the existing event long-poll endpoint with cancellation and retry backoff. It reconciles bounded bootstrap/history responses and keeps loaded pages. Backgrounding stops the poll; foregrounding reloads before reconnecting. Cross-origin HTTP redirects are rejected and cookies are disabled. Sign-out revokes the session before deleting local account data. On the first Release launch, the app imports the prior React Native server, appearance, accent and haptic preference. It restores a bearer only when it is bound to that same server and a stable account ID, then performs the normal session validation. It preserves the push installation ID for that account. Existing native settings are never overwritten. The original Expo keys remain available for rollback; pending React Native outbox items and unsent drafts are not converted.

## Known limits

Native APNs registration and delivery are implemented alongside Expo; signed-device APNs delivery/background clearing remain acceptance requirements. Release distribution signing is verified. Live plugin OAuth/services, camera and microphone interruptions, physical haptics, and sustained production-history performance still require device/server acceptance. Advanced plugin workspace actions are implemented but are not all covered by UI automation. See [the feature and error-handling audit](docs/FUNCTIONAL-PARITY.md) and [the cutover gates](docs/PARITY.md); retain the React Native app during acceptance.
